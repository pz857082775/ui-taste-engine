# 进化协议（Evolution Protocol）

本文件定义知识如何进入、成长、退化、死亡。**没有协议的"自我学习"就是自我污染。**

---

## 一、知识生命周期（五阶段）

```
候选 Candidate → 复现 Reproduced → 稳定 Stable → 默认 Default → 公理 Axiom
  confidence 1      confidence 2     confidence 3   confidence 4   confidence 5
                                                  ↓
                                          stale → archived（衰减路径）
```

| 阶段 | 进入条件 | 权力 | 退出条件 |
|---|---|---|---|
| **候选** (1) | 1 次观察，有来源与证据 | 只能出现在"建议"里 | 再有 1 次独立复现 → 2；60 天未复现 → archived |
| **复现** (2) | 2 次独立任务均成立 | 可写进提示词"建议项" | 第 3 次无反弹 → 3；出现反例 → 降回 1 |
| **稳定** (3) | 3 次独立任务成立，无反弹 | 可作为该场景默认值使用 | 晋升闸门通过 → 4；90 天未用 → 2 |
| **默认** (4) | 过回归集（均分不降 >2）且写入规范文件 | 成为 `website-ui-designer` 的硬规则 | 出现系统性反例 → 3；180 天未用 → archived |
| **公理** (5) | 跨 ≥3 个项目验证 + 人工书面批准 | 不受衰减影响，只有人工能改 | 仅人工可撤销 |

**关键约束**：`confidence ≥4` 不可自动获得——必须经过回归集 + 写回规范两步，防止"自己说了算"。

---

## 二、晋升闸门（Promotion Gate）

晋升前逐条检查，任何一条不过就打回：

```
[ ] 1 来源完整：sources 有 ≥1 个可追溯来源（任务 id / URL / 截图路径）
[ ] 2 证据充分：evidence ≥ 3，且来自 ≥2 个不同任务
[ ] 3 单一变量：这条规则的生效不依赖其他未记录的参数
[ ] 4 边界清晰：applies_to 写清了平台/页面类型，不是"所有地方都适用"
[ ] 5 反例检查：反例库中不存在与它冲突的活跃卡（有则先裁决）
[ ] 6 回归通过：跑 evals/cases.yaml，总分不下降 >2，且无单例下降 >5
[ ] 7 可回滚：记录"如果这条错了，怎么撤回"（改哪个文件、恢复什么值）
```

命令对应：`kb.py promote <ID>`（检查 1-5）→ 手动跑回归（6）→ 人工确认（7）→ 写回规范。

---

## 三、衰减机制（Decay）

**为什么必须衰减**：设计趋势会过时、平台规范会变、模型会升级。不衰减的知识会变成新教条。

| 触发 | 动作 |
|---|---|
| 90 天未被 `use` 引用 | confidence -1（最低到 1） |
| 180 天未引用 | 标 `status: stale`，不再进入生成前检索 |
| 365 天未引用 | 移入 `knowledge/archive/`（保留可查，不参与决策） |
| 被新技术替代（如平台改版） | 立即 stale，并注明替代者 |

命令：`kb.py decay`（按 last_used 批量执行，输出变更清单）。

---

## 四、冲突裁决（Conflict Resolution）

同一 `applies_to` 下出现矛盾规则时，按以下顺序裁决，**并记录理由**：

1. **证据强度**：evidence 多者胜
2. **范围具体度**：`applies_to` 更具体者胜（"医疗工作台"优先于"全部后台"）
3. **时间新近**：同强度时新者胜（记录日期）
4. **可测性**：能被测量验证的胜（"对比度 4.5:1"胜"看起来更舒服"）
5. **人工裁定**：仍冲突则上报，**不许静默选一个**

裁决结果写成一条 J 卡：`{场景} 下，A 优先于 B，因为 {理由}`。

---

## 五、宪章（不可自我修改的部分）

以下内容**引擎不得自动修改**，只能由人工批准变更：

1. 评分三轴与权重（Distinction 40 / Craft 30 / Usability 30）
2. 10 项验收条
3. 反例库的删除（只能新增、降级，不能删）
4. 置信度的定义与晋升门槛
5. 本文件的裁决顺序

**理由**：如果模型能改自己的评分标准，"自我进化"就会退化成"自我讨好"——分数越来越高，界面越来越差。

---

## 六、进化日志（必须写）

每次晋升/降级/裁决，追加一行到 `knowledge/EVOLUTION.log`：

```
2026-10-22 | PROMOTE | P-003 强调色预算 3-5 次 | 1→4 | 回归 +3.2 | 写入 design-system-spec.md
2026-10-22 | DECAY   | M-011 玻璃卡片阴影 | 3→2 | 90 天未用
2026-10-23 | CONFLICT| 营销页入场 vs 后台入场 | 裁决：按页面类型分治 | 见 J-004
```

日志是审计线：三个月后回看，能知道"为什么现在是这条规则"。

## 七、一次完整进化示例

```
1. 任务：给一家咖啡店做品牌页（H5）
2. 生成用了"超大背景字 + 低饱和 + 12px 行距"
3. 用户反馈："有点压抑，想更透气"
4. 采集（Capture）：
   场景 H5/营销页；参数：行高 1.5，背景字透明度 16%
   结果：用户嫌压抑
   结论（候选）：移动端正文行高 ≥1.7 更透气
5. 下一次任务再用 1.7 → 用户未提意见（复现，confidence 2）
6. 第三次在另一项目用 1.7 → 通过（stable，confidence 3）
7. 跑回归集，均分 +1.4，无单例下降（过闸门）
8. 写回 platform-matrix.md「H5 正文行高 ≥1.7」→ confidence 4
9. 记日志
```

这就是"自我进化"的真实形态：**慢、有证据、可回滚**。任何"一次就升级"的机制都是幻觉。
